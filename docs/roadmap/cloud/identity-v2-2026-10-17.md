# Identity V2 — device key and BLE device proof (2026-10-17)

Status: **Implemented and validated on the board end to end with the local backend.** App flow (phone) not built yet.

## Design

- Key: ECDSA **P-256** (mbedTLS, ESP-IDF 4.4 has no Ed25519), private scalar 32 B in NVS `xuna_life/devkey`, created once after BLE init (RF on → hardware RNG), verified by read-back before use. A corrupt stored key is **never** replaced (would silently change the identity the cloud pinned); proofs then report `not_ready`. Signing is deterministic (RFC 6979).
- Message (shared with backend `identity/domain/device_proof.py`, golden SHA-256 `2ec55d34…cb4c` checked on both sides):
  `"xuna.proof.v1" 0x00 | nonce[32] | petId[16] | purpose u8 | generation u32 LE | SHA-256(payload)`; for Bind the payload is the device's own 65-byte public key.
- BLE characteristic `7a6e000d` (WRITE + READ), capability **byte 3 bit 0** (`01 08 bf 01 0f 03 60 09`):
  - request 40 B: `ver=1, size=40, purpose, 0, requestId u32 LE (≠0), nonce[32]`;
  - response 141 B: `ver=1, size=141, purpose, status, requestId, generation, publicKey[65], signature[64] (r||s)`; status 0 idle, 1 pending, 2 ok, 3 invalid request, 4 unsupported purpose, 5 not ready, 6 failed.
  - One proof in flight; BLE callback only queues; signing runs in the main loop; a session change resets the value. **Projection (purpose 2) is refused** so an app cannot obtain device attestation for data it made up.
- Pure parts in `xuna_core` (`base/Sha256.h`, `identity/DeviceProof.h`: message, `ProofService`); hardware part `include/DeviceKey.h`; GATT budget 20 of 32 handles.

## Limits / follow-ups

- Flash encryption is off: someone with USB access can read `devkey`. Before launch: flash encryption + secure boot (threat model T1).
- Signing blocks the loop ~74 ms once per proof; acceptable for a rare bind.
- Mobile flow (read caps byte 3, write request, read proof, call backend) **built 2026-10-18** (Firebase Auth, `--dart-define=XUNA_API_BASE_URL`); host tests only. The 40-byte request uses a GATT long (prepared) write because the app does not raise the MTU; this has not been run against the board from a phone yet.
- The real pet was bound only in the local dev database `xuna_local`, not a hosted service.
